# 泛化改造：让插件对陌生环境可预测

> 状态：草稿（未发布到 issue tracker —— `gh` 不在 PATH）
> 来源：2026-11-12 两轮 grill 的结论

## Problem Statement

一个只用自己机器验证过的人写了个 DSH 插件，想给社区用。别人的环境和他不一样：

- **宿主版本不同。** 插件压的两个能力（会话技能目录、右侧栏 tab 注册）没有第三方先例，DSH 一升级就可能断；现在断了的表现是**整块不出现**，用户只会觉得「这插件坏了」。
- **语言不同。** 界面文案按浏览器的 `navigator.language` 二选一，不看宿主的语言；分组标题是写死的中文。英文界面的用户会看到中文分组名。
- **技能集不同。** 归类表是作者自己那 45 个技能的名单。别人装的是别的技能，命中不了，只能靠关键词推断，推断不出就落进「其他」。
- **平台未知。** 代码里没有一行平台相关的东西，但也没人说过它在 macOS / Linux 上能不能跑。

结果就是：插件在作者机器上很好用，在别人机器上**要么消失、要么半中文、要么大量技能挤在「其他」**。这种失败不报错、不解释，比装不上更糟。

## Solution

把「只在我的机器上成立」的四处假设变成显式契约：

1. **声明能跑在哪。** `engines.dsh` 只写实测过的范围；安装时 npm 会拦，不靠用户猜。
2. **缺能力要说话。** 拿不到数据源时不再静默消失，而是显示一个能解释的空态：哪个能力缺了、当前 DSH 版本大概是什么情况。
3. **跟随宿主语言。** 界面文案接宿主的 locale 服务，英文为默认，中文做翻译；分组标题同时带中英两版。
4. **归类以规则为主。** 关键词规则负责陌生技能，具名表降为「覆盖层」，用户还能在 `~/.dsh/skill-dashboard/taxonomy.json` 改自己机器上的归类，不用碰包内文件。

## User Stories

1. 作为一个英文用户，我希望插件的标题、按钮、空态都是英文，这样我不用猜中文按钮是什么意思。
2. 作为一个中文用户，我希望在宿主切到中文时界面跟着变中文，这样我不需要单独改配置。
3. 作为一个装了自己技能的 DSH 用户，我希望我的技能自动落到合理的分组里，而不是全挤在「其他」。
4. 作为一个装了自己技能的用户，我希望对自动归类不满意的条目能自己改，且改完立即生效。
5. 作为一个不想改包内文件的用户，我希望我的归类覆盖放在我的用户目录里，升级插件不会丢。
6. 作为一个在 Linux 上跑 DSH 的用户，我希望插件不因为是 Windows 上开发的就打不开。
7. 作为一个 DSH 版本较旧的用户，我希望安装时就被提示版本不够，而不是装完发现按钮点了没反应。
8. 作为一个版本较新的用户，我希望插件在能力还在时正常工作，而不是被过窄的版本上限挡住。
9. 作为一个遇到能力缺失的用户，我希望看到「这个 DSH 版本没有 X 服务」这样的说明，而不是空白面板。
10. 作为一个维护者，我希望新增一处宿主依赖时能有一处地方统一声明和探测，而不是散落在各处。
11. 作为一个给这个仓库提 PR 的人，我希望改归类只要改一个 JSON，不用碰 JavaScript。
12. 作为一个给这个仓库提 PR 的人，我希望 CI 能告诉我 JSON 改错了哪里，而不是合并后才发现。
13. 作为一个评审者，我希望这次改造有一个可测试的接缝，而不是只能靠截图确认。
14. 作为一个关注隐私的用户，我希望插件不上报任何使用数据。
15. 作为一个从 npm 安装的用户，我希望包里有 README、LICENSE、taxonomy，而不是缺文件。

## Implementation Decisions

### 唯一接缝：一个纯函数

**`composeDashboard(input)` —— 纯函数，无 IO。** 输入是原始目录、默认 taxonomy、用户覆盖表、语言；输出就是客户端直接渲染的那个 payload（含每个技能的处境、触发语、中文说明、是否推断而来，以及本地化后的分组标题与计数）。

主机侧一次组装，客户端只负责画。理由：

- 现在「归类 → 分组 → 计数」散在主机和客户端两边，同一个概念算两次。
- 纯函数是这里**最高、也唯一需要的接缝**：主机集成测试喂假服务，归类/本地化/推断全部可测；客户端不再有可测逻辑，也就不需要第二处接缝。

### 能力探测

- 一处声明：插件依赖的每个宿主服务（技能目录、右侧栏 tab、会话作用域、对话输入、locale）各有一条可用性判断。
- 探测结果进入 payload，客户端据此决定渲染正常视图还是空态。
- 数据源优先级保持现状：会话技能目录 → 会话作用域 + skills → 全局 skills；全失败才空态。

### 版本与兼容

- `engines.dsh` 只声明实测范围（`>=0.2.2-rc.1`），并按 `dsh-context` 的格式补 `dsh.compatibility`。
- 不声明版本上限：新版本是否可用由运行时探测决定，不用安装期拦截。
- 平台：不写任何平台分支；README 注明「三平台理论上可用，Windows 实测」。

### 归类与覆盖

- 关键词规则留在代码里（它是逻辑，社区改它需要 review）；具名表 + 处境定义留在 `taxonomy.json`。
- 用户覆盖表：`~/.dsh/skill-dashboard/taxonomy.json`，**与包内同结构**，按技能名合并（覆盖层优先，包内的补齐）。
- 覆盖表读不到、格式错、半截写坏 —— 一律当成「没有覆盖」，并在 payload 里带一条可显示的提示。

### 本地化

- 处境定义带 `title`（中文）与 `titleEn`（英文）两个字段；客户端按宿主 locale 选。
- 界面文案接宿主 locale 服务注册自己的命名空间；拿不到 locale 服务时退回 `navigator.language`。
- 英文是默认文案，中文是翻译。

### 分发

- npm + GitHub，不做遥测。

## Testing Decisions

- **什么算好测试**：只测 `composeDashboard` 的输入输出，不测渲染、不测宿主。
- **测哪些**：归类推断（现有 9 例迁进来）、覆盖表合并（有/无/坏）、本地化选择（zh/en/未知）、能力探测三档降级、计数。
- **测试工具**：`node --test`，零依赖；现有 `tools/check-*.mjs` 合并成测试。
- **先例**：仓库现有的 `tools/check-taxonomy.mjs`、`tools/check-inference.mjs` 就是这个思路，迁进 `node --test` 而不是另起框架。
- **不测**：浏览器渲染 —— 用截图人工确认，README 记录这一点。

## Out of Scope

- 安装 / 卸载 / 更新 / 启停技能（ADR 0001 已定：只读）
- 「未安装技能」的浏览
- 遥测、匿名统计
- 跨 minor 版本的兼容承诺
- 项目级（跟仓库走）的覆盖表 —— 只做用户级
- 机器翻译：本机没有 `translator` 服务，中文说明靠 `zh` 字段 + 社区 PR
